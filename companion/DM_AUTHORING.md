# Authoring values and sources after the vault cutover (2026-11-15)

The Obsidian vault `vault/` (Discourse Graphs notes) is the only authored source of values, their sourcing, the paper register, link rows, method and join records, the audit log and the classifier tables. These files are GENERATED, never edited by hand: global_config.json, other_config.json, paper_links.csv, paper_register.csv, nonbrain_audit_log.csv, sourcing_records.jsonl, source_basis.csv, unsourced_kind.csv, declared_values.csv, sculpt_measures.csv, the two growth sources files, equations.jsonl, body_provenance_12p5_required.json, growth_web_12p5.json, tools_config.json, constant_overrides.json, TRUSOMA_JEPA_REFERENCES.csv, and the databases. Not generated: the frozen constant log (vault/Meta/Frozen.md), the appendix [V] lines and the {cid:} code tags (committed by hand).

Commands (all in tools/dm; each writes vault notes, rebuilds relations.json, regenerates every file and runs the check):
- `python tools/dm/value_add.py value --key K --target global|other --value JSON --entries Q12 --state "..." --status S [--meaning ..] [--paper P --locator L --quote Q --value-in-source V --species-age S --transfer T]`
- `value_add.py learner --module M --name N --value JSON --entries K18 --note "{cid: K18} [K18] unit; rule PA2" --status S --paper P --locator L --quote Q --cls human_fetal|... --species ... --stage prenatal|...`
- `value_add.py set --key K [--value JSON] [--status S] [--meaning ..] [--state ..] [--entries a,b]` (a changed status or meaning of a constant that is in the frozen log is also written as an override)
- `value_add.py evidence --key K --paper P --locator L --quote Q ...`; `paper --id p-x --first-author .. --year .. --citation ..`; `basis --species-age TEXT --kind .. --species .. --stage ..`; `record --json '{...}'`
- Audit items: `python companion/audit_log/audit_log.py set|add ...` (writes the Issue note, regenerates the CSV).
- By hand in Obsidian or an editor: edit the note, then `python tools/dm/build_from_vault.py write` and `python tools/dm/check_all.py`.

Then put the {cid: ...} tag the tool prints on the consumer line and commit (the appendix's learner value table is a generated block since 2026-11-15, plan section 19; a hand-written reading note above the block is optional and, when present, is compared with the vault). The pre-commit build (build_sourcing_db.py --check) refuses a commit whose generated files differ from the vault, so a hand edit of a generated file fails there.

Rules that did not change: no value in code, a db reference per value, a source-found status needs a verbatim quote, locator and paper, no adult values, a new constant needs an appendix [V] entry read FIRST, provenance_check and the isolation guard.

Rollback: `git tag pre-dm-cutover` (the tree before the cutover); the retired value tools run only with TRUSOMA_LEGACY_VALUE_TOOLS=1 on that tree.

Note names: '#' in a key is written '~' in the note name (a '#' in a wiki-link is a heading); the Claim's key property keeps the real key.

## Added 2026-11-16: other people's nodes and relations (imports through the plugin)
- Notes the plugin imports from another space land in `vault/import/<space>/` and carry `importedFromRid`. They are not read by our tools (never a value, never sourcing) and the folder is ignored by git. A note with `importedFromRid` is skipped even if it is moved into `vault/DiscourseGraph/`.
- `vault/relations.json` is therefore a MIXED file: the relations our notes imply are generated and checked as before; a foreign relation (it carries `importedFromRid`, or one of its ends is a resource id of another space (`orn:` or `https://`), or one of its ends is a note imported from another space) is carried through unchanged by `build_from_vault.py write`, accepted by the check, and left alone by `ingest_gui.py`. Foreign relations cannot be regenerated from a fresh clone: they come back with the next import. A relation with an end that is no note at all (left over when one of our notes is deleted or renamed) is not foreign: the check refuses it and a regeneration drops it.
- Fields the plugin adds to one of OUR relations when it is published (`publishedToGroupId`, `lastModified`, `authorId`, `tentative`) are kept on regeneration; the check compares id, type, source, destination and created only.
- The public extract (`make_public_extract.py`) writes only our own relations and our own grammar: nothing imported goes public, and the group ids the plugin writes when it publishes (`publishedToGroupId` on a relation, `publishedToGroups` on a note) are removed from the extract.
- Tested with fixtures only (`test_semantic.py`, cases 16 to 23; field names read from the plugin source at 1ae4c00 and present in the installed release 1.8.0, vault/.obsidian/plugins/discourse-graphs/main.js). Not yet done: a real publish and import between two vaults through the plugin's sync, which needs sync mode and a group.

## Added 2026-11-16: readable note bodies
- Every node note (not the table rows in vault/Tables) has a body of plain sentences DERIVED from its own properties by `tools/dm/readable.py`: what the value means when a `meaning` property exists, its key and value, its status in words (a model choice or an unresearched value is said to be unsourced), the quote and locator of an Evidence note, the statement of a test, the item of an audit Issue, the citation of a Source, with wiki-links to the notes it names.
- The body is never authored and never read back. Every tool write rebuilds it, `build_from_vault.py write` rebuilds a stale one (after an edit in Obsidian), and the check refuses a body that differs from the derivation. To change what a note says, change its properties.
- No description is invented: a value without a `meaning` property (1,623 of 1,772 configuration values on 2026-11-16) states only its key, value and status. Titles are derived too (see the sections on titles below); a note id comes from its stable name, never from its title.

## Added 2026-11-16: an Evidence note that opposes a Claim

- Two properties on the Evidence note: `opposes` (a list of links to Claim notes) and `opposes_basis` (the passage where the vault itself states the conflict). They also work on a growth web value note; nothing else on a record note is authored this way.
- The basis must be found word for word in some vault note (a Claim's state, a value's unit text, a growth web test statement). The check refuses an opposition without one, so no opposition is written from memory.
- An opposing Evidence never makes a value sourced: a Claim with a source-found status still needs its own supporting Evidence. One Evidence cannot both support and oppose the same Claim.
- A relation drawn in Obsidian from an Evidence note to a Claim with the type opposes is written into `opposes` by `ingest_gui.py apply`; the check then refuses it until `opposes_basis` is added.
- Entered so far: 4 relations for 3 stated conflicts (Ashwell 2012 against the SCN join JN-1; Yew 1999 and Herb 2023 against each other's hypothalamic peptide onsets; Fidzianska 2002 against the Forger 1987 peak of motoneuron death). Tests: cases 31 to 35 of test_semantic.py.

## Added 2026-11-16: titles, Parameter notes, the reader's own notes, and the value guard

- **A note's id no longer depends on its title.** The id and the ids of its relations derive from the note's stable name (the key or record id). When the title is not `prefix + name`, the name is kept in the property `dg_name`. Tools find a note by that name (`dmlib.title`, `dmlib.link`, `dmlib.target_of`); never build a file name or a link by hand.
- **Titles are generated**, like bodies (`readable.title`): a record Claim is titled by its own sentence, a growth web mechanism by what acts on what, a sourced value by its meaning or by `key = value` and how it is sourced, an Evidence note by what the source says and the paper, each with the stable name in brackets. `build_from_vault.py write` renames a note whose title is stale and rewrites every link to it; the check refuses a note renamed by hand. Nothing is invented: a value with no `meaning` states its key and value.
- **A setting with no source is a Parameter note** (`PAR - key`), not a Claim: a model choice, a value not researched, one with no source found, or one that cites the design only, with no Evidence. Inside the tools it is the same value with the same id, read by the same generator. When it gains a source and Evidence it becomes a Claim on the next regeneration, and every link follows.
- **Your own writing goes under the heading `## Notes`** at the end of a note. Everything from that heading on is yours: the check does not read it, a regeneration and a retitle keep it word for word, no tool reads a value from it, and the public extract leaves it out. Text written above that heading is replaced by the generated body.
- **Two relations are now derived from what the notes already say**: a method, value or join record is produced by its paper (Source produces Claim, from the record's `source`), and a growth web value supports the sourcing record it names (Evidence supports Claim, from its `record`).
- **The value guard**: `python tools/dm/value_guard.py check --retyped --added dg_name` compares the working tree with the tag `pre-dg-remediation`: the generated files byte for byte, every note by its id with every link resolved to the id it points at, and the rows of the three databases. Run it after any change to the vault's form. A removed or changed property, a lost note or a link that points elsewhere fails it.
- Entered from the record: 7 Questions (the four rungs of RESEARCH_GRADE_PLAN_2026-11-09.md, the two pre-registrations, the growth probe) and 2 pre-registered Hypotheses, each quoted word for word.
- Left as they are, with the reason: Issues are work items and the grammar has no relation from an Issue to a value, so most stay unlinked; no Claim is said to address a Question, because the record's answers are Results and the grammar has no Result to Question relation; the Conclusion type stays unused because it is part of the shared lab schema; templates and a canvas need a person at Obsidian.

## Entry forms in Obsidian (added 2026-11-17)
The split (USER 2026-11-17): what is copied goes through a strict form; what is judged is written freely and admitted afterwards.
- The plugin's source is TypeScript in `demo/apps/forms` (`src/`, built with esbuild by `scripts/build.ts`, the way the Discourse Graphs Obsidian plugin is built; `pnpm run check-types`, `pnpm run lint` and `pnpm run build` there). The built files in `demo/apps/forms/dist` are not committed.
- Install once per machine, and again after the plugin's source changes: `python tools/dm/forms_plugin/install.py`. It builds the plugin when the built files are missing or older than the source (this needs Node and pnpm, and `pnpm install` in `demo/` once), copies three files to `vault/.obsidian/plugins/trusoma-forms` and adds `trusoma-forms` to the list of enabled plugins. Desktop only. The Python command is a plugin setting (default `python`).
- Every note has a Copy note button in its header (also a command and a note-menu entry): it copies the whole note, properties included, as it stands in the editor.
- Commands (command palette, or the clipboard icon in the left ribbon): Enter a Result; New draft; Save a draft to the graph; Enter a passage of a paper; Change a value. Every form works by keyboard: Tab, Enter, Ctrl+Enter for the main button, Esc to cancel.
- A Result: pick the experiment (the record file follows it), type a few words of the line and pick it from the record, trim it if less than the line is meant, choose the reading. "Check only" shows the note as it will be written. "Check and save" writes it, regenerates, runs the full check (about 10 seconds) and opens the note. A refusal is shown at its field and nothing is written.
- A claim or a question: "New draft" opens an empty note in `vault/Drafts`. The first line is the claim or the question. Everything below it is your reasoning, as long as you like. No tool reads `vault/Drafts`, so a draft never fails a check or stops a commit, whatever it is called. "Save a draft to the graph" (the button "Save to graph" on the draft) turns it into a note of the graph when you say so: the first line becomes the statement, the rest stays yours under `## Notes`, and the draft file is removed. A claim needs at least one Result for or against it and a line of a record one of those Results rests on. A question needs only its short name; its record is a dated line that the admission adds to `companion/audit_log/QUESTIONS_ASKED.md`.
- A value: the first press checks and shows the value now, the value after, and the code lines and notes that read it. The second press writes. Learner constants are not changed in the form (their appendix line and code tag must agree): use `value_add.py`.
- A passage of a paper: the paper must already be in the register (`value_add.py paper`, after the five-field check). The form cannot check a paper's words, so copy them as they stand.
- No rule lives in the plugin. Each form sends one JSON request to `tools/dm/form_api.py`, which runs the vault's own checks on the vault plus the one candidate note before anything is written, writes through `dmlib`, and after a failed check puts back the exact bytes of every file it touched. The same door works from a terminal: `echo '{"action":"lists"}' | python -B tools/dm/form_api.py`.
- One writing request at a time. A save, an admission, a value change and a passage each hold a lock (`local/form_api.lock`, held by the operating system on an open file, so it is let go when the process ends and there is never a stale lock to clear). A second writing request waits up to 60 seconds and is then refused with "Another save is still running" and nothing written. Reading requests do not wait. A refused save undoes itself and nothing else: only the files its own process wrote are put back (Python reports each file the process writes, removes or renames; a file that changed in the same seconds some other way is its author's). What you type under the Notes heading of another note, or a note or draft you begin, at any moment of the save stays. If you change a note after the save wrote it, your change is kept: merged into the note as it was when the two changes are in different lines, otherwise the note is put back and your version is copied to local/form_api_kept, and the form says where.
- Tests: `python tools/dm/test_form_api.py` (54 cases in a throw-away worktree, about 2 minutes; a save that answers ok leaves a passing check, a refusal leaves `git status` unchanged). `tools/dm/forms_click_test.cjs` drives the forms in real Obsidian by keyboard on a throw-away copy; its measured output for 2026-11-17 is in local/dg_guard/forms_click_test_run_2026-11-17.json.
- Not in the forms yet: Hypothesis and Experiment notes, a Result's links to a configuration value, adding a paper to the register, learner constants, editing a note that exists. These stay with `value_add.py`.
- Buttons on the notes themselves (added 2026-11-17, late), each also a command and an entry in the note's menu: on a draft, "Save to graph" (called "Admit this draft" until the wording review of 2026-11-17); on a Result, "Draft a claim from this Result" (the draft remembers the Result, and the admit form opens with it under "Results for the claim": move it if it stands against); on a Question, "Draft a claim that addresses this"; on an Experiment, "Enter a Result for this experiment"; on a body or other value, "Enter a passage for this value" and "Change this value". The status bar counts the drafts that wait and opens them. What was saved is said in the status bar, not in a notice, because a notice covers the note's buttons.
